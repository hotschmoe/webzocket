## tools/tidy.zig

`zig build tidy` measures source with Zig 0.17.1's `std.zig.Ast`. The blocking
`test` step runs tidy before the short fuzzer and existing test runner; compilation can run in
parallel. Tidy is a build lint, not another end-to-end test. `-- --table` prints
Markdown rows, source totals and repository totals. The longest-function total
is a maximum; other totals sum groups, including their separate deficits.
Wall time uses the awake clock and includes discovery, git and ratchet checking.

The program is copied between webzocket, rich_zig, zunk and teak. All repository policy lives in the
typed `config` block at its top: source roots, skipped directory names, group
rules, generated-file markers, script exclusions and additional banned helper
names. A compiled block keeps this policy small, checked by Zig and colocated
with the program; a separately parsed configuration file would add another
input and failure path. The ratchet remains runtime data so tightening does not
recompile the tool. There is no shared package or repository-name detection.

Webzocket's style scope is `src/`, `tools/`, `support/`, `build.zig` and `test_runner.zig`.
Root patterns ending in `/` include descendants; other patterns match exactly.
Groups are each direct directory under `src`, `src/*.zig`, `tools`, `support`,
the root build file and the test runner. Group rules match prefixes in order; `directory`
selects the next directory component when present, otherwise the rule's name.
Discovery skips `.git`, `.zig-cache`, `zig-out`, `zig-pkg`, `.archive`,
`node_modules`, and does not follow symlinks. A file with `GENERATED`
or `Generated by` in its first eight lines is excluded and named in every report.

`held_files` in `tools/tidy_ratchet.zon` is a hand-maintained list of source
paths. Each file has its own group, excluded from its directory's counts, and
must meet every style target independently of its stored numbers. It must
exist, be in scope and not be skipped or generated. Duplicate and noncanonical
paths fail. Updates preserve the entire list, including when a file is missing;
they never remove entries. Webzocket holds every new Zig source file: the owned assert,
the five fuzzer modules, `tools/tidy.zig`, the four `conn*.zig` files and the eight `sim*.zig` files.
The list is authoritative in the ratchet.
Seam inventories and globals may be nonzero; style targets are zero, with
longest function at most 70. Moving a held file
out of a group also moves its assertion demand and surplus credit.

The columns mean:

- `files`, `lines`, `functions`: included files, physical lines (a final newline
  adds no empty line), and function declarations with bodies. Bodiless
  prototypes and function pointer types are excluded. `type_functions` is the
  subset with explicit return expression `type`; it remains in `functions`.
- `long_lines`: lines exceeding 100 Unicode code points, including comments
  and ordinary quoted literals. Tabs count as one column; display widths are
  not modeled. A line whose AST token is `multiline_string_literal_line` goes
  into `literal_long_lines` instead. This reports embedded JavaScript, shaders
  and other multiline data without ratcheting them as Zig style violations.
- `long_functions`, `longest_function`: physical span from `fn` through the
  closing body token, inclusive of signatures, comments and blank lines. Type
  constructors are exempt from both metrics; their methods count.
- `assertions`: calls whose final identifier is `assert`, regardless of receiver.
  Ownership belongs to the innermost function, including nested methods.
  `trivial_functions` counts bodies with exactly one top-level AST statement,
  including a lone return or the owned assert's conditional panic. Such functions
  contribute neither assertion demand nor credit. Other functions require two
  assertions on average within their group: `assertion_deficit` is
  `max(0, 2 * nontrivial_functions - assertions_in_nontrivial_functions)`.
  Extra assertions in one nontrivial function can cover another's deficit.
  `functions_no_assert` still reports all bodies with no assertion calls.
  Sites sample under-asserted nontrivial functions, rather than numeric deficits.
- `usize_fields`, `sized_fields`: struct fields typed `usize` or `?usize`, versus
  explicit `uN`/`iN` or their optional form. Tuple fields count. Union members,
  enum tags, aliases, pointers, arrays and slices do not. `isize` is not `usize`.
- `self_recursion`: functions calling themselves. `mutual_recursion`: unordered
  function pairs with calls in both directions, once per pair. Bounded stacks
  assign container scopes and function ownership; measurements scan the flat
  AST. Bare names resolve through enclosing containers to file scope. Field
  calls resolve through a uniquely named local container, `self`, `Self`, or
  the caller's first parameter. Ambiguous names, imports, aliases, function
  pointers, arbitrary receiver types, indirect calls and cycles longer than two
  are not resolved. The first-parameter heuristic can mistake a function-pointer
  field for a method. Comptime and syntactically bounded recursion still count.
- `while_true`: while nodes with literal `true` conditions. This neither proves
  other loops bounded nor inspects exits within these loops.
- `camel_case`: lowercase-initial function names with an uppercase ASCII letter,
  excluding type constructors. Escaped identifiers are not normalized.
- `allocation`, `clock`, `environment`, `threads`, `files_io`, `processes`: potential banned
  calls, once per category per call. One call can count in several categories.
  These expose seams; they do not prove an allocation happens after startup.
- `globals`: container-member `var` declarations at file scope or in any struct,
  union or enum, including containers declared inside functions (static locals).
  `threadlocal` and extern variables count; `const`, instance fields and ordinary
  call-local variables do not. Membership comes from the AST, independent of
  function ownership. Each declaration counts once, even inside generic types.
  This inventory exposes persistent state for the simulator's repeated runs;
  it does not distinguish a cache from a registry or prove semantic determinism.
- `scripts`: git-tracked `.sh`, `.py`, `.mjs`, `.js` and `.ps1` files, excluding
  `src/gen/js/` (shipped application code) and `ref/` (read-only prior art).
  Shipped JS is not tooling; counting it as tooling would measure the wrong debt.
  Untracked Zig files are measured too. `tests` counts AST test declarations in
  every discovered nongenerated Zig file, even outside style scope. Held files' tests belong to
  their individual group; all other tests and all scripts belong to `repository`,
  so totals do not double-count. Amendment 3 retains 38 existing declarations as debt;
  held/new source files still require zero. The stored test count is an ordinary downward ratchet.

The standard allocation field-call names are `alloc`, `alignedAlloc`,
`allocSentinel`, `allocWithOptions`, `allocAdvanced`, `create`, `realloc`, `remap`,
`dupe`, `dupeZ`, `dupeSentinel`, `allocPrint`, `allocPrintSentinel`, `append`,
`appendSlice`, `appendNTimes`, `appendFlattened`, `ensureTotalCapacity`,
`ensureTotalCapacityPrecise`, `ensureUnusedCapacity`, `addOne`, `addManyAsSlice`,
`resize`, `put`, `getOrPut`, `fetchPut`, `putNoClobber`, `initCapacity`,
`toOwnedSlice`, `toOwnedSliceSentinel`, `readFileAlloc`, `readFileAllocOptions`,
`utf16LeToUtf8Alloc` and `createMap`. `join` and `concat` also match through
`std.fs` or `std.mem`. Bounded forms such as `appendAssumeCapacity`,
`putAssumeCapacity` and `bufPrint` are excluded. Receiver types are not inferred:
GPU `resize` and our bounded `Buffer.append` can be false positives; aliases and
wrappers with different names can be missed. Native resource creation allocates too.

Clock calls contain `std.time` or `Io.Clock`, or use the clock/timestamp names
in `clock_names`: libc and kernel clock queries, `sleep`, `nanosleep`, `usleep`,
Windows timing and Mach time. `std.Io.sleep` and `std.Io.Timestamp.now` count as clock access. Environment
names cover libc `getenv` and setters, standard environment helpers and Windows
get/set APIs, plus `init.environ_map` and `minimal.environ` chains. Thread calls
contain `std.Thread` or `Io.Threaded`, use `pthread_`/`thrd_` APIs, clone or thread
helpers; `io.concurrent`, `io.async` and raw futex operations count too. Clone counts as both thread and process
access because flags determine what it creates.

File calls contain `std.fs` except `std.fs.path`, `Io.Dir`, `Io.File`, or use the
standard file names in `file_names`. Path helpers operate on strings and do not
count as IO; allocating `join` still counts as allocation. `stdio_names` adds
libc stdio, including `fopen`/`fopen64`, `fread`, `fwrite`, `fclose`, seeking,
stdio output, temporary files and pipe streams, plus `dlopen`/`dlclose`/`dlsym`.
`std.DynLib` calls count as file access. `raw_file_names` covers descriptor IO,
metadata, directories, links, mappings, sync and file watches through `std.c`,
`std.posix` and `std.os.linux`. Common names such as `read`, `close` and `remove`
require a raw receiver, so an application collection's `remove` is not file IO.
Raw reads/closes of sockets also count: descriptor kind is not inferred.

`processes` covers `std.process.spawn`, `run`, `replace`, libc/kernel exec,
fork, spawn, wait, process identity and signals, and Windows process launch APIs.
It counts call sites, not the number of children. `popen`/`pclose` count as both
file and process access. Ambiguous `wait`/`kill` require a raw receiver or bare
call; child instance `wait`/`kill` are not inferred, while their spawn is counted.

Token chains ignore whitespace and comments. One file-level `const` alias to a
field-access namespace is recognized for raw APIs, `std.Thread`, `std.DynLib`
and `std.process`. This is lexical inventory: it does not resolve local shadows,
alias chains, arbitrary receivers, imports, syscall numbers, function pointers,
native extern calls with other names or differently named application wrappers.
Name-only matching can overcount same-named application methods. The arrays in
the program are the complete name lists, reviewed against Zig 0.17.1's standard
sources; they also cover common libc externs a program can declare itself.

Webzocket adds allocation helpers `acquireOrCreate`, `grow`, `setupCompression`, `writeBuffer`;
environment helpers `readEnv`, `readEnvBool`; and IO helpers `fill`, `writeAll`,
`closeSocket`, `closeStream`. These are conservative call inventories, including bounded
in-memory writers. Tidy
necessarily uses allocation, a clock, files and git; held files allow and ratchet
these seam inventories and globals.

Every discovered `build.zig.zon` must have the same decoded
`minimum_zig_version`, including tool manifests. Missing values, invalid syntax
and disagreements fail independently of ratchets. This checks manifest agreement,
not CI's installer or agreement between separately reported repositories.

`-- --table --root <path>` opens another tree read-only, measures all discovered
Zig files (including root-level files), and groups them by first directory or
`*.zig`. It never reads or writes a ratchet or applies the held list. The
same directory and generated exclusions apply. Scripts use filesystem discovery
there, including untracked files, because fetched packages need not have git
metadata. Tests are reported without enforcing zero. `--root` and `--update`
cannot be combined. The foreign source and manifests are never modified.

The ratchet is parsed with `std.zon`. Its metric-name header fixes numeric row
order. Stored metrics are long lines/functions, longest function, deficit,
usize fields, recursion, literal infinite loops, camelCase, banned-call counts,
globals, scripts and tests. Sizes, assertions, trivial functions and literal long
lines are reported only. Every stored number must match exactly. Decreases fail until
`-- --update` records them; increases are refused even by update. A raise is
legitimate in three cases: a count that was always there has become
visible (tidy learned to see it, or an implicit operation was made explicit); a
call moved from one group into another, lowering the first by at least as much;
or a long function in old code was split, adding a function to the assertion
average. The stored number is then edited by hand and the change report explains
why.
Held-file regrouping can likewise remove surplus assertion credit from a group;
this accounting change needs an explained hand edit. New metrics are seeded by
hand. Replacing tidy itself re-seeds only its seam inventories; its style stays
at target. The complete snapshot is validated before writing. A new group must
start with zero long lines/functions, deficit, usize fields, recursion,
while-true, camelCase and tests,
and longest function at most 70. Seam counts may be nonzero. Existing debt is
seeded once by hand; update cannot bootstrap it. Removed groups measure zero
until update drops them. Failures name group, metric, before/after and at most
twenty current file:line samples. Vanished sites have no remaining location.

The initial webzocket baseline was seeded once by parsing `zig build tidy -- --table`
into the 18 stored columns with a one-off Python command, then formatting the ZON.
No tool update was used to bootstrap legacy debt. Future changes use `-- --update`.

One startup allocation reserves `State`; it is released at shutdown. Limits:
2 MiB per input, 4,096 files/directories/held paths, 65,536 entries per directory,
2,048 functions and 4,096 containers per file, 524,288 tokens/nodes, nesting
depth 256, 128 groups, 512 bytes per path, 20 sites per metric/group, 256 KiB
report buffer and 64 MiB parser scratch. Git output is capped at 2 MiB and
4,096 names. Limits return named errors and fail; nothing is silently omitted.
No owned heap memory is acquired after startup. The standard AST/ZON parser
requests temporary allocations from the reserved scratch, reused between inputs.
This compiler-workspace exception permits the required standard parser API
without arena growth. Standard IO and process internals are outside that owned
workspace guarantee. Traversal uses a bounded queue; syntax ownership uses
bounded stacks. The standard parser may recurse; tidy's functions do not.

## src/assert.zig

An owned panic check keeps invariants active under every optimize mode. It is deliberately
independent of the standard debug assertion policy so release builds cannot erase these checks.

## src/fuzz.zig

The executable owns IO, time, failure recording and one startup workspace allocation. The core
checker receives that workspace and never opens a socket or starts a thread. The 128-case gate
covers all 100 profiles; smaller campaigns fail coverage. A timed run stops on a 64-case boundary
and also has a ten-million-case ceiling. The background gate budgets 30 seconds.

Failure files contain the exact input bytes; adjacent metadata records seed, case number and
probe name. Replay reconstructs expectations from the generator and then replaces the input
with the saved bytes. Replay is tied to this generator revision, rather than claiming that old
seeds remain meaningful after the oracle changes. Recordings are transient, not golden outputs.
Panic recording covers library traps as well as typed oracle failures. Length overflow and short
request lines are ordinary rejected profiles. A provider maximum of zero with a failing allocator
is an ordinary accepted profile: it is how zunk's dev server forbids overflow storage, and a frame
that fits the static buffer must still be read. The `forbidden-fragment` probe exposes fragment allocation even with ample caller storage.

## src/fuzz_generate.zig

Independent frame serialization avoids a writer/reader pair agreeing on the same bad encoding.
Expected payloads exist before masking and fragmentation. SHA-1 uses the standard one-shot API
over a joined key and GUID, independently of the library's streaming hash. All input and expected
output storage has declared maxima: 150,000 wire bytes, 140,000 payload bytes and eight messages.
Generation and checking use sized counters. Fixed arrays bound temporary compressor storage.

Compatibility profiles preserve permissive behavior until an intentional protocol change is
authorized: non-minimal data lengths, unmasked input, invalid UTF-8, invalid close bodies, weak
handshake keys, duplicate headers, missing Host, non-GET methods and malformed CRLF separators.
Truncation is an incomplete parse, not a typed EOF error: neither public parser has an EOF input.
The one-byte schedule checks every prefix of each generated stream. It is a safety/property
check over prefixes, not a claim that the library can diagnose transport EOF without a caller.

## src/fuzz_profiles.zig

Profiles cover all reserved opcodes, each control opcode, fragment accumulation limits,
in-flight fragment teardown, a signed 64-bit length, and compression with back-references past
the 32 KiB window. Standard DEFLATE generation complements an independently assembled stored
block with a stripped sync-flush tail. HTTP profiles vary required headers and line endings.
Profiles 84, 85 and 96 cover static-storage limits, signed lengths and length overflow; 97 through
99 cover short request lines. All expect typed errors and participate in coverage accounting.

## src/fuzz_check.zig

Every frame input runs with bulk, one-byte and seeded chunk schedules, including both pooled
and unpooled overflow storage. Bulk and one-byte runs
use different poison bytes. Caller buffers have checked canaries; bounds-checked builds and
independent expected messages detect premature payload use. This is not an instrumented proof
that no internal load touches unused capacity. Two preallocated pool buffers allow compressed
input and decompressed output to coexist without a pool fallback. Other scratch is bounded at
2 MiB and reset per observation. The empty fallback allocator makes unexpected allocation fail.

The writer is compared byte-for-byte against the independent encoder's header, and the reader
checks the same generated frames. Oversized control headers are writable but unparseable as valid
messages; the oracle expects LargeControl for these opcode/length combinations.
Handshake prefixes run in a caller-constructed public State with bounded header arrays. Reply
checks cover the accept hash, response headers and compression advertisement. They avoid an
HTTP server, handshake pool, scheduler, thread or socket oracle.

## src/fuzz_allocator.zig

Allocation accounting wraps reserved scratch rather than the process heap. Live bytes must
return to zero after Reader.deinit, including rejected and incomplete fragments. Call counts
detect attempted fallback allocation even if the underlying empty allocator refuses it.

## src/proto.zig

Frame lengths reject the RFC 6455 signed bit and any payload plus header/mask that cannot fit
`usize` before addition or narrowing, in every optimize mode. The provider maximum bounds
overflow storage only: a frame that fits the reader's current buffer is read whatever the
maximum says. Enforcing it on the static path was tried and undone, because a caller that sets
the maximum to zero to forbid overflow storage (zunk's dev server) would lose every frame.
Fragment accumulation separately bounds the combined payload; decompression uses the bounded
buffer writer. Server `max_message_size` supplies the provider maximum; client `max_size` does
so unless a caller supplies a provider, in which case that provider owns the limit.

Known difference for the rewrite: a configured maximum smaller than the static buffer has no
effect; the limit a reader enforces is the larger of the two.

## src/conn.zig, conn_frame.zig, conn_handshake.zig, conn_utf8.zig

One endpoint of a WebSocket connection as a state machine over bytes: server or client role, no socket, no
thread, no allocator after init, no clock. It is the first rewritten module (D1) and is exported as
`webzocket.conn` (`conn.Conn`, `conn.Config`, `conn.Event`, `conn.Error`, `conn.SendError`, `conn.Eof`,
`conn.Stats`). The server's own type already owns the name `webzocket.Conn`, so the new one lives in a
namespace until the old server goes; then it takes the short name. The old server, client and reader are
untouched.

API shape: a poll loop, not events returned from `feed`.

- Input: `recv_space()` and `received(n)` let a caller read a socket straight into the receive buffer;
  `feed(bytes)` is the same with one copy. It accepts at most the free space and returns the count, so the
  caller offers the rest again after polling.
- `poll()` returns one `Event` (`opened`, `message`, `ping`, `pong`, `closed`) or null when it needs
  input, or a typed `Error`. Event slices (message data, ping payload, close reason, request target) are
  valid until the next `poll`, `feed` or `recv_space`.
- Output: `output()` is the queued bytes, `output_taken(n)` frees them. `start_client`, `send_message`,
  `send_fragment`, `send_ping` and `send_close` queue frames; `end_of_input()` is the outcome of a
  transport end in the current state; `tick(now_ms)` checks the two deadlines.

Why poll: a returned event slice has to live somewhere. With events returned from `feed` one call can complete
many messages, so either every message needs its own storage or the caller gets a list of slices that the
next frame overwrites. With a poll loop one message buffer is enough, the caller decides when to drain, back
pressure is the free space of the receive buffer, and a frame header or payload is consumed as it arrives, so
the receive buffer only has to hold a header (and the whole HTTP head during the handshake). Turned down:
events returned from `feed` (above), and a callback interface (puts the caller's code inside the state
machine and hides the order of effects). The zunk reload connection reads one 256-byte buffer by hand
(`buf`, `pos`, `message_len`) and sets the provider maximum to 0 so that nothing can allocate. With `Conn`
that loop is: `feed` or `received` after a read, `poll` until null, write `output()` and call
`output_taken`; the handshake, ping, close and masking rules are the library's, and nothing can allocate.

Storage and limits (D7): the caller passes three slices at init. The receive buffer must hold the HTTP head
(request or reply) and at least 64 bytes; a head that does not fit is `HandshakeTooLarge`. The message
buffer is the largest assembled message; a frame or the running total of fragments above it is
`MessageTooLarge` and is detected from the header, before the payload is read. The send queue holds whole
frames; a frame bigger than the queue is `TooLarge`, one that does not fit now is `QueueFull`; both are
returned, counted in `Stats.sends_refused` and never partially written. `Stats` also records the high
water of each buffer, so a check can compare use against what was declared. An automatic reply that does
not fit waits: the newest ping's pong is kept (an earlier unsent pong is replaced and counted in
`pongs_coalesced`, which RFC 6455 section 5.5.3 allows) and a close echo is kept; they are written as soon
as `output_taken` frees room, and new sends are refused while one waits so the order on the wire holds.

Checks in a frame header run in this order: reserved bits, opcode, control frame rules (not fragmented,
payload at most 125), mask by role (a server rejects an unmasked frame, a client a masked one), length form
(no sign bit, minimal), then the state rules (a continuation needs a message in progress, a new data frame
needs none), then the size limit. The receiver unmasks while it copies into the message buffer and checks
UTF-8 incrementally, so a code point may be split across fragments and an invalid byte is rejected where it
arrives. Close frames: one byte is a protocol error, the code must be 1000 to 1003, 1007 to 1014 or 3000 to
4999, and the reason must be UTF-8. Close codes sent after an error: 1002, 1007 (invalid UTF-8) or 1009
(too large). A server that rejects a handshake queues a short `400` reply; a client that rejects a reply
sends nothing.

Closing: `send_close` moves to `closing`; the peer's data and pings are still delivered until its close
arrives. A peer close is answered with its code (no reason) unless this side already sent one. After this
side has queued a close it answers no more pings. After a close or an error nothing is delivered and
nothing is produced; bytes still fed are counted in `ignored_bytes`.

End of input is `clean` (closing handshake complete), `failed`, `in_handshake`, `in_frame`, `in_message`,
`without_close` or `during_close`. Time is a parameter: `init` and `send_close` take `now_ms`; with
`handshake_timeout_ms` or `close_timeout_ms` set, `tick` fails the connection with `Timeout`. Client mask
keys come from a ChaCha generator seeded by `Config.mask_seed`; the caller supplies the 16 key bytes of the
opening handshake to `start_client`. Nothing inside reads an entropy source. A client with an all-zero
seed is `InvalidConfig`: mask keys must not be predictable, so the seed has no usable default.

permessage-deflate is out of scope for this step: a server ignores an extension offer and replies without
one, a client offers none and fails a reply that names an extension (`ExtensionNotOffered`), and any
reserved bit is `ReservedBits`. Also not done: custom reply headers, subprotocol negotiation (a server
ignores offers, a client fails a reply that names one), Origin checks, a `426` reply for a wrong version,
keepalive timers, and splitting a long message into frames (the caller chooses fragments).

Closed in `Conn` (the old code keeps them):

- proto.zig: a maximum below the static buffer has no effect (closed: the message buffer is the limit);
  non-minimal lengths (`NonMinimalLength`); text UTF-8 (`InvalidUtf8`, also across fragments); close payload
  length, code and reason (`BadClosePayload`, `BadCloseCode`, `InvalidUtf8`); truncation without a typed
  outcome (`end_of_input`); fragment storage that asks an allocator even when it would fit (no allocator);
  `writeFrameHeader` emitting oversized control headers (`send_ping` refuses more than 125 bytes with
  `TooLarge`; the old function stays as it is until the old reader goes).
- handshake.zig: keys not checked as base64 of 16 bytes (`BadKey`); `Connection` matched as a substring (it is a
  token list now); methods other than GET (`BadMethod`); optional `Host` (`MissingHost`); malformed CRLF
  separators, bare CR or LF, control bytes and folded lines (`BadLineEnding`, `BadByte`, `BadHeader`);
  truncation (`end_of_input`). Duplicate `Host`, `Sec-WebSocket-Key`, `Sec-WebSocket-Version` and
  `Sec-WebSocket-Accept` headers are `DuplicateHeader`.

Still open, and why: the `Upgrade` header is accepted as a token list that contains `websocket` (RFC 6455
asks for a header containing the value; the old parser wants exactly one), so a request the old parser
rejects (generator class 93) opens in `Conn`; this is deliberate and counted as `conn_looser`. Subprotocol
and extension negotiation, custom reply headers and compression are listed above. The request target is
checked for printable ASCII only. Header count and size are bounded by the receive buffer, not by a separate
limit.

## src/sim.zig and src/sim_*.zig

`zig build sim -- --seed N --steps M [--seeds K] [--seconds S] [--replay file]` is the simulator for `Conn`.
The executable owns IO, the clock (only for `--seconds`) and one startup allocation of its workspace; every
other file is deterministic and has no global state. A seed names a run; each run is made of sessions, and a
session is seeded by the seed and its index, so `--replay` of a failure file re-runs exactly that session
(honest or adversary) or the corpus pass. The run of a seed is executed twice, in memory filled with
different bytes, and the two trace hashes must match (this also catches reads of uninitialized memory). A
failure prints the seed, session, checker and detail and writes `zig-out/sim/seed-N-session-I.txt`, which
is a recording of the seed and session, not golden output.

- sim_world.zig, an honest session: client and server `Conn` joined by two pipes (sim_pipe.zig) that deliver
  in chunks from one byte up, delay segments, and can be cut at any delivered byte or stalled. Storage sizes
  are chosen low on purpose, so refused sends and limits are ordinary. A seeded workload sends texts and
  binaries (fragmented, with pings between fragments), pings and closes, from both sides, with both sides
  closing at once in a quarter of the closes. Checkers: every message arrives once, in order, byte-identical;
  every ping is answered by a pong with its payload (an unanswered ping is allowed only for coalesced pongs and
  for pings that reach a side that already sent its close); both sides end closed with the code and reason
  of the other side's close (or the echo); after a close or error nothing is delivered and no byte is
  produced; a refused send happens only when the queue could not hold the frame and is counted exactly; the
  outcome at a cut or stall is the typed end of input that an independent frame scanner (sim_wire.zig)
  computes from the delivered bytes; every buffer has canary bytes around it and the high water marks stay
  within what was declared; each stream a `Conn` emits is fed, as it is emitted, to the old
  `proto.Reader` (random static buffer sizes, a bounded fixed-buffer allocator), and what the Reader
  returns must equal what the receiving `Conn` delivers, including pongs and closes. The client request is
  also parsed by the old `Handshake.parse`.
- sim_adversary.zig: one side replaced by a generator of damaged byte streams. 56 classes: reserved bits,
  reserved opcodes, fragmented and oversized control frames, wrong mask for the role, both non-minimal
  length forms, the sign bit, stray continuations, data frames inside a fragmented message, frames and
  fragment sums over the limit, bad UTF-8 (single, split, truncated), bad close payloads, 23 damaged requests
  and 13 damaged replies, valid handshake variants (case, token lists, extension and subprotocol offers),
  valid closes followed by garbage, and valid streams cut at a random byte. Each class has one expected error,
  one expected close code and one expected output (the 400 text, nothing, or valid pongs then one close
  frame). The same stream also runs with whole-buffer feeding, and the two runs must agree on events, error,
  output and end of input.
- sim_corpus.zig: the existing tester's generator (fuzz_generate.zig) fed to `Conn` in both roles, 200 cases
  per seed. A stream the old Reader accepts must be accepted by `Conn` in at least one role with the same
  messages, or be rejected with one of the errors that class is known to differ by (listed in the code and
  counted per class in the output as `conn_stricter`: mask by role, non-minimal lengths, UTF-8, close payloads,
  RSV1, weak or duplicate handshake keys and headers, wrong method, missing Host, malformed CRLF). A stream the
  old code rejects must be rejected by `Conn` with the matching error in at least one role; the only
  accepted exception is class 93 (above).
- Gates: `zig build test` runs a fixed-seed run (seeds 1 and 2, 3000 steps) after tidy and the short fuzzer;
  `zig build test-heavy` also runs `sim-heavy`, a 30 second campaign of 200,000-step seeds.

Of the 38 existing test declarations, the simulator makes redundant "Reader: fuzz" and "mask" (the old Reader
reads generated masked and unmasked frames of every length class with random buffer sizes, and the unmasking
is checked against an independent encoder), and the fragment-accumulation block of "Fragmented". They are
kept in this step. The others test code the simulator does not reach (servers, sockets, pools, compression,
the buffer provider).

## build.zig

`src/assert.zig` is a named module (`assert`) that the library, the fuzzer and the simulator import by name,
because a file may belong to one module only and `conn.zig` has to use the owned assert. A consumer gets it as
an import of the `webzocket` module; no extra step or option appears. Only the root package registers tidy,
fuzz, sim and existing test steps. Consumers configure the
public module and its options; packaging includes only the build files, src and LICENSE.
The assert and fuzz sources under src are not imported by websocket.zig and do not enter a
consumer's runtime module graph. The build file itself uses the owned assert from src.
